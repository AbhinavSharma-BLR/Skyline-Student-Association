# .agents/rules/database.md — Database and Prisma Obligations

**Stack:** Local PostgreSQL (native or Docker) + Prisma ORM + Better Auth Prisma adapter.
**Applies to:** All tasks involving schema changes, migrations, data access, seeding or database tooling.

> IMPORTANT: This project uses Prisma ORM with local PostgreSQL. Supabase-specific features (auth.uid(), RLS, supabase client, supabase storage, NEXT_PUBLIC_SUPABASE_* env vars) MUST NOT appear anywhere in the codebase.

---

## 1. Prisma Client Usage

### Singleton Pattern

```typescript
// lib/prisma.ts
import { PrismaClient } from "@prisma/client"

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined }

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    log: process.env.NODE_ENV === "development" ? ["query", "error", "warn"] : ["error"],
  })

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma
```

- Always import `prisma` from `@/lib/prisma`. Never instantiate `new PrismaClient()` elsewhere.
- Only one PrismaClient instance per Node.js process.

### What Not to Do

```typescript
// WRONG — direct instantiation
const prisma = new PrismaClient()

// WRONG — Supabase client
import { createClient } from "@supabase/supabase-js"
const supabase = createClient(url, key)

// WRONG — floating point money
const total = item.pricePaise / 100  // never divide paise; keep as integer
```

## 2. Schema Rules

- All model IDs: `String`, `@default(cuid())`.
- Better Auth model IDs: `String`, no `@default()` — generated by Better Auth.
- All timestamps: `DateTime` (stored UTC). Display in `Asia/Kolkata` at the UI layer.
- Money: `BigInt` in Prisma. `CHECK` constraints enforced via custom SQL migration.
- Enum-like string fields: constrained via SQL `CHECK` constraints (Prisma cannot express these natively).
- Prisma `@@map()` names use `snake_case`. Prisma model names use `PascalCase`.
- No hard-delete on confirmed purchases, cashbook entries or handover snapshots via application code.

## 3. Migrations

### Creating a New Migration (Development)

```bash
npx prisma migrate dev --name <descriptive-name>
```

- Generates a timestamped folder in `prisma/migrations/`.
- Applies migration to `skyline_dev` database.
- Runs `prisma generate` to update the client.
- Commit the generated migration file.

### Applying to Demo or Production

```bash
npx prisma migrate deploy
```

- Applies pending migrations; never creates new migration files.
- Run before starting the demo server.

### Adding Check Constraints

Prisma cannot express PostgreSQL `CHECK` constraints natively. Add them via a custom SQL migration:

```bash
# Create a blank migration file
npx prisma migrate dev --create-only --name add_domain_constraints
# Then edit prisma/migrations/TIMESTAMP_add_domain_constraints/migration.sql to add CHECK statements
npx prisma migrate dev  # applies it
```

Always commit custom SQL migrations alongside `schema.prisma`.

### Never Do

- Never hand-edit a migration file after it has been applied (`_prisma_migrations` table marks it as applied).
- Never run `prisma migrate reset` on the demo machine. Only on local dev.
- Never add a migration that breaks the existing applied history without a compensating migration.

## 4. Transactions and Concurrency

### Use $transaction for All Multi-Table Writes

```typescript
await prisma.$transaction(async (tx) => {
  // Use tx.model.method() inside; not the global prisma client
  await tx.booking.create({ data: { ... } })
  await tx.purchase.create({ data: { ... } })
}, { isolationLevel: Prisma.TransactionIsolationLevel.Serializable })
```

### Row Locks via Raw SQL

```typescript
// Seat reservation — lock activity row first
const [activity] = await tx.$queryRaw<Activity[]>`
  SELECT id, capacity FROM activities WHERE id = ${activityId} FOR UPDATE
`

// Variant reservation — lock in sorted ID order to prevent deadlocks
const variants = await tx.$queryRaw<Variant[]>`
  SELECT id, "stockTotal", "stockReserved", "stockSold"
  FROM variants WHERE id = ANY(${variantIds}::text[])
  ORDER BY id FOR UPDATE
`
```

### Raw SQL Safety

```typescript
// CORRECT — tagged template literal (parameterized)
const result = await prisma.$queryRaw`SELECT * FROM users WHERE id = ${userId}`

// WRONG — string interpolation (SQL injection)
const result = await prisma.$queryRaw(`SELECT * FROM users WHERE id = '${userId}'`)
```

Only use `Prisma.sql` or tagged template literals for raw queries. Never use `$queryRawUnsafe` unless explicitly justified and reviewed.

### External Calls Outside Transactions

Do not call email or payment providers inside `$transaction`. Pattern:
1. Write intent to DB inside transaction.
2. Commit.
3. Call provider after commit.
4. On provider failure, a retry job picks it up from the persisted record.

## 5. Money Arithmetic

```typescript
// All amounts stored as BigInt
const totalPaise = items.reduce(
  (sum, item) => sum + item.unitPricePaise * BigInt(item.quantity),
  BigInt(0)
)
// NEVER use parseFloat, toFixed or divide paise in business logic
// Display only: (Number(totalPaise) / 100).toFixed(2)  — only in presentation layer
```

## 6. Auth Tables

Better Auth owns the `user`, `session`, `account`, `verification` tables via the Prisma adapter:

- Do not manually write to `account.password` — Better Auth manages hashing.
- Do not manually write to `session.token` — Better Auth manages session tokens.
- Domain code may read `user.id`, `user.email`, `user.name` from the session object provided by `auth.api.getSession()`.
- Do not join across `account` or `session` tables in domain queries unless reading for audit purposes.

## 7. Seeding

- Seed file: `prisma/seed.ts`.
- Run via: `npm run db:seed` (configured in `package.json` as `prisma.seed`).
- Seed must be idempotent: use `upsert` or check-before-insert for demo accounts.
- Demo passwords: set from environment variable or a clearly-labelled dev default. Never hard-code real passwords.
- Seed creates: demo accounts, initial `ClubSettings`, demo `MembershipPeriod`, demo `Activity`.

---

## 8. Test Database

- Use `DATABASE_URL_TEST` for integration tests. Never run tests against `skyline_dev`.
- Test setup: apply migrations via `prisma migrate deploy` against `skyline_test`, then seed test fixtures.
- Test teardown: truncate or recreate the test DB between test runs.

---

## 9. Observability

- Log slow queries (>200 ms) in production.
- PrismaClient error events must be caught and logged with request ID.
- Never log: raw SQL with substituted values, session tokens, password hashes, file paths.
